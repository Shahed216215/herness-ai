# Mira HFM v0.2 Runtime Configuration

Status: source-only operator guide. This document does not authorize a database migration, secret change, Render update, PR merge, or deployment.

## Runtime identity and project bootstrap

The project bootstrap endpoint accepts only the server-verified session principal. It creates the initial owner and ADMIN membership in Neon using the dedicated authority-issuer connection. It does not accept a caller-supplied actor ID.

## Neon capability groups and LOGIN principals

Migrations 005, 007, 008, and 009 define the HFM capability model:

- `mira_hfm_memory_writer`: NOLOGIN capability group for authority consumption and Memory repository operations, constrained by forced project RLS.
- `mira_hfm_authority_issuer`: NOLOGIN capability group for project-scoped owner/membership reads, initial owner/membership inserts, and one-time authority/audit inserts. It cannot read or write Memory payloads.
- `mira_hfm_memory_writer_login`: LOGIN principal inheriting only the Memory writer group.
- `mira_hfm_authority_issuer_login`: LOGIN principal inheriting only the authority issuer group.

Migration 009 creates no password. Set each LOGIN role password directly in Neon Console, then create the corresponding connection URLs there. Do not paste passwords or connection strings into chat, source control, issue comments, or logs.

## Render environment variable names

Configure these on the existing `mira-ai-agent` service only after the user explicitly approves the production configuration change.

| Variable | Required value / purpose |
|---|---|
| `MIRA_HFM_MEMORY_WRITE_ENABLED` | `true` only after writer migration and preflight are approved |
| `MIRA_HFM_MEMORY_DATABASE_URL` | Neon connection URL for `mira_hfm_memory_writer_login` |
| `MIRA_HFM_MEMORY_WRITER_ROLE` | `mira_hfm_memory_writer_login` |
| `MIRA_HFM_AUTHORITY_ISSUER_ENABLED` | `true` only after issuer migration and preflight are approved |
| `MIRA_HFM_AUTHORITY_ISSUER_DATABASE_URL` | Neon connection URL for `mira_hfm_authority_issuer_login` |
| `MIRA_HFM_AUTHORITY_ISSUER_ROLE` | `mira_hfm_authority_issuer_login` |
| `MIRA_VAULT_ACTIVE_KEK_VERSION` | Active vault key version, initially `v1` |
| `MIRA_VAULT_KEK_V1` | Base64-encoded 32-byte key; set through the secret manager, never in source/chat |
| `TAVILY_API_KEY` | Optional public-web research provider key; if absent, the API returns manual-import fallback |

The existing application/session database configuration is separate from the HFM writer and authority-issuer URLs. Never point either HFM role URL at an owner, admin, runtime, or Neon superuser connection.

## Configuration-only runtime diagnostic

The authenticated admin-only endpoint is `GET /api/hfm/runtime/readiness`.

It reports only whether the authority-issuer, Memory-writer and Vault configuration shapes are present. It does not connect to Neon, initialize either pool, read payloads, or perform writes. Its response always identifies database connectivity as `NOT_TESTED`, runtime readiness as false, and production readiness as `NOT_CERTIFIED`. It never returns URLs or key material.

The diagnostic checks these exact environment variable names:
- `MIRA_HFM_AUTHORITY_ISSUER_ENABLED`
- `MIRA_HFM_AUTHORITY_ISSUER_DATABASE_URL`
- `MIRA_HFM_AUTHORITY_ISSUER_ROLE`
- `MIRA_HFM_MEMORY_WRITE_ENABLED`
- `MIRA_HFM_MEMORY_DATABASE_URL`
- `MIRA_HFM_MEMORY_WRITER_ROLE`
- `MIRA_VAULT_ACTIVE_KEK_VERSION`
- `MIRA_VAULT_KEK_V1` (and the versioned equivalent for a later active key)

A successful diagnostic response is not evidence that Neon is reachable or that HFM can read or write Memory.

## Readiness gates

Before production use:

1. Review and explicitly approve the required HFM migrations on the production branch.
2. Create and password-protect the two LOGIN principals out-of-band.
3. Configure the two separate Neon connection URLs and exact role-name variables.
4. Set the vault KEK through Render's secret environment interface and verify key-version configuration.
5. Verify each pool preflight succeeds and rejects excess privileges.
6. Run the repository CI suite and an authorized staging end-to-end test.
7. Review PR #70 and explicitly approve merge/deployment separately.

No local filesystem or phone storage is a Memory source of truth. A missing Neon connection, key, or authority must fail closed; no local fallback is permitted.
