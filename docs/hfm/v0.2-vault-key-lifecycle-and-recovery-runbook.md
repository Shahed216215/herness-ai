# Mira HFM v0.2 — Vault Key Lifecycle and Recovery Runbook

Status: SOURCE-ONLY OPERATIONS DESIGN. This document does not authorize secret changes, database backups/restores, migrations, Render changes, deployment, or production activation.

## 1. Security invariants

- Private and restricted Memory payloads are encrypted before database persistence using a per-record data-encryption key (DEK), wrapped by a versioned 256-bit key-encryption key (KEK).
- The envelope `keyVersion` identifies the KEK required to unwrap its DEK. Decryption must use that exact version; never silently substitute the active key.
- `MIRA_VAULT_ACTIVE_KEK_VERSION` selects the KEK for new envelopes. Keep every KEK needed by retained envelopes available until a separately tested rewrap-and-verification process proves it is no longer needed.
- Keep KEKs outside the database and source control, in the approved secret manager. Never place key material in chat, logs, Git, backup manifests, or database rows.
- A database backup without its corresponding KEK versions is not a recoverable encrypted-Memory backup. A KEK backup without the database is not a complete recovery set.
- Do not disable, delete, overwrite, or rotate away an old KEK merely because a newer version is active.

## 2. Controlled KEK rotation

The current crypto implementation supports versioned KEKs for envelope decryption and new writes, and computes idempotency digest candidates across configured KEK versions. It does not provide an automated bulk envelope rewrap/rotation job.

1. **Prepare:** create a new independent 32-byte random KEK in the approved secret manager. Assign the next unused version (for example, `v2`). Do not derive it from the old KEK.
2. **Preflight:** confirm the old active KEK and all prior KEKs remain present and recoverable. Verify a protected test envelope encrypted under each retained version can be decrypted in an isolated test environment.
3. **Stage:** configure the new version alongside all retained old versions. Do not remove or overwrite the old version.
4. **Activate:** after explicit change approval, change only `MIRA_VAULT_ACTIVE_KEK_VERSION` to the new version. New writes then use the new KEK; existing envelopes continue to require their recorded `keyVersion`.
5. **Verify:** create and read back synthetic test records under the new version; verify old synthetic envelopes still decrypt; verify a missing/wrong KEK fails closed. Do not use real user payloads for rotation tests.
6. **Rewrap (not currently implemented):** before retiring any old KEK, a separately designed and approved job must unwrap each retained envelope's DEK with its recorded old KEK, wrap it with the new KEK using the correct AAD, update the envelope atomically, preserve record identity/revision and audit the operation. Verify every affected record after the update. No such job is authorized or evidenced by this runbook.
7. **Retirement gate:** retain the old KEK until a complete inventory proves no retained envelope references it, all required backups and restore points have a documented compatible key set, idempotency reconciliation windows have expired, and restore tests pass. Require explicit approval before disabling or destroying it.

If any step fails, stop. Keep all old keys intact and keep production readiness uncertified. Never attempt speculative decryption or key substitution.

## 3. Backup and restore recovery set

A recoverable HFM backup must be treated as a coordinated set:

- Neon database backup/snapshot or supported point-in-time recovery reference, including schema/migrations and the relevant project data.
- A separately protected escrow/recovery copy of every KEK version needed by the encrypted envelopes in that recovery point.
- A manifest containing only non-secret metadata: backup/snapshot identifier, database/project/branch identity, creation time, migration/schema level, KEK version identifiers (not values), application commit, and operator/checkpoint reference.
- Recovery instructions and access to the required secret manager. Never store KEK values alongside the database snapshot.

Before relying on any backup, verify that the provider actually completed it and that its retention/expiry and restore semantics are known. A branch or snapshot name alone is not evidence that data can be restored.

## 4. Restore procedure — isolated target only

1. Obtain explicit approval naming the exact backup/snapshot, target branch/database, and permitted restore scope. Never restore over production as part of a test.
2. Restore into a new or explicitly designated isolated recovery target. Preserve the source database and snapshot unchanged.
3. Verify schema/migration level and role/RLS configuration before application access. Do not grant broad owner/superuser access to the application.
4. Load the matching KEK versions securely into the isolated runtime. Do not print values or expose them in diagnostics.
5. Run read-only structural checks first: expected tables, constraints, RLS enabled and forced, policies, triggers, row counts, and envelope key-version inventory.
6. Using synthetic test records or an explicitly approved minimal test sample, verify decryption with the recorded KEK versions and correct record AAD. Confirm missing/wrong keys fail closed.
7. Verify project isolation and least-privilege login roles. Check that no local phone/filesystem fallback becomes a source of truth.
8. Record results, hashes, restore target, snapshot reference, code commit, key-version identifiers, and any gaps. Do not claim recovery success until application-level readback and integrity checks pass.
9. Keep the recovery target isolated until a separate review and approval authorizes any cutover.

## 5. Recovery failure handling

- Missing KEK, authentication-tag failure, malformed envelope, unknown key version, or integrity mismatch: stop and mark the affected recovery check `FAIL` or `INCONCLUSIVE`; do not rewrite or delete the envelope.
- Missing snapshot, expired snapshot, unknown retention, or unverified provider restore: mark recovery `NOT_VERIFIED`.
- Database restored but KEKs unavailable: mark encrypted Memory recovery `BLOCKED_KEY_UNAVAILABLE`.
- Never report PASS based only on a successful snapshot creation or database connection.

## 6. Current implementation boundary

- Versioned envelope encryption/decryption: source implementation and contract tests exist.
- Old/new KEK compatibility: contract test exists when both key versions are configured.
- Idempotency digest candidates across configured KEKs: contract test exists.
- Automated bulk rewrap, key retirement inventory, managed KEK escrow workflow, and end-to-end backup/restore validation: **NOT_IMPLEMENTED / NOT_TESTED**.
- No backup or restore was performed by this document change.
- No production secret, database, Render setting, deployment, or PR merge was changed.

## 7. Required gates before production certification

1. Approve and document the secret manager and KEK escrow/recovery ownership.
2. Implement and independently review the envelope rewrap job before any old-key retirement is contemplated.
3. Establish an authoritative inventory linking retained envelope key versions to backup/restore points without exposing payloads or key values.
4. Perform a disposable, isolated restore using a verified backup and its matching KEK set.
5. Run synthetic decrypt, integrity, authority, and cross-project isolation checks against the restored target.
6. Review recovery evidence and obtain separate explicit approval for production activation.

Until these gates are met: `VAULT_KEY_RETIREMENT=NOT_APPROVED`, `BACKUP_RESTORE_RECOVERY=NOT_VERIFIED`, and `PRODUCTION_READINESS=NOT_CERTIFIED`.
