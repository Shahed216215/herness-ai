3. LEGACY FAMILIES

Blueprint §12 enumerates:
- HFM-LOG-001: event identity and project scope are mandatory.
- HFM-LOG-002: sequence ordering is validated.
- HFM-LOG-003: previous-hash linkage is verified.
- HFM-LOG-004: event hash uses the declared canonical profile.
- HFM-LOG-005: duplicate event identity is reconciled.
- HFM-LOG-006: checkpoint authenticity and chain head are verified.
- HFM-LOG-007: broken chain fails closed.

Prototype C §11.7 references HFM-LOG-001 through HFM-LOG-007 and says they are extended with concurrent append and crash-injection fixtures. It does not provide a one-to-one revised definition for each reused identifier in that section.

Crosswalk status: REVIEW_REQUIRED. The Blueprint definitions are individually identifiable, but Prototype C's extension semantics cannot be silently folded into the same immutable definitions. Preserve the Blueprint meaning and record C's extended fixture scope as a separate proposed definition or explicit version/supersession only after owner review.

D. Prototype E registry rules

Prototype E §9.2–9.4 requires one definition per test ID, explicit requirement mappings, execution status/evidence and distinct coverage classifications. This is the governing registry design principle, not a legacy alias list.

4. PROHIBITED MAPPINGS WITHOUT REVIEW

- Do not map HFM-CHAIN-001 to HFM-LOG-004 merely because both relate to canonical event hashing.
- Do not map HFM-CHAIN-004 to HFM-LOG-005 merely because both concern duplicate identity.
- Do not map HFM-CHAIN-011 to HFM-LOG-006 merely because both concern checkpoints.
- Do not map Prototype C's extended HFM-LOG-001..007 fixtures onto the Blueprint definitions without explicit version/supersession semantics.
- Do not map the current eight Phase 2 runtime test-suite IDs to DR-08 chain IDs. They cover different scopes and do not execute the chain protocol.

5. PROPOSED MIGRATION RULE

1. Preserve each historical identifier and source-document context.
2. Create a new immutable canonical testId for each distinct definition.
3. Use aliases only where one historical ID maps unambiguously to exactly one canonical definition.
4. Where a legacy ID was reused for materially different behavior, preserve separate source-scoped definitions and mark the legacy mapping AMBIGUOUS/REVIEW_REQUIRED.
5. Record source commit/blob SHA, source section, fixture scope, expected behavior and evidence status for each mapping.
6. Never mark a test TESTED_PASS from a source description or ID mapping; execution evidence is required.
