1. CENTRALIZED TOOL AUTHORITY POLICY

The tool-level policy table and decision function were extracted from services/mira-work-execution-engine.js into services/mira-tool-execution-policy.js.

The execution engine imports and re-exports TOOL_POLICIES/getToolPolicy, and retains its seven-check execution sequence. The low-level tools/index.js executeTool() entry point now calls the shared checkToolSafety() before invoking a registered wrapper. A denied or unclassifiable decision returns a structured BLOCKED result and the wrapper is not invoked.

This adds a second enforcement point:
- executeWork() applies the complete seven-check execution gate before runTool().
- tools/index.js executeTool() independently enforces tool-level policy, so direct callers of executeTool()/services/tool-runner.js cannot bypass human-only or non-autonomous tool policy.

The raw tools object is still exported for capability inspection and dedicated dispatch paths. Direct calls to tools[name].execute() or direct imports of individual tool modules do not automatically pass through executeTool(); these remain subject to the separate callsite review below.

4. DISPATCH AND DIRECT-WRITE CALLSITE REVIEW

The reviewed routes directory contains no direct runTool(), executeTool(), or .execute() tool-wrapper calls. The admin task-execution route uses executeWork().

Reviewed server.js direct execution paths:
- /api/admin/backup directly calls knowledge_backup.execute(); the route is guarded by requireAdminPermission(PERMISSIONS.BACKUP_RESTORE).
- /api/admin/restore directly calls knowledge_restore.execute(); the same permission gate applies and confirm must equal true before the wrapper is called.
- seo_workflow_history directly calls its read/history wrapper only after the named authenticated admin browser-session gate.
- seo_workflow_review_decision is sent through mira-seo-review-dispatch, which independently requires an authenticated named admin browser session.
These are dedicated server/admin dispatch paths, not ordinary model-generated tool calls. They intentionally do not use executeWork(); their authority boundary is the corresponding admin permission/session and, for restore, explicit confirmation.

Other reviewed paths:
- services/mira-autonomous-worker.js sends calculator and web_search tasks through executeWork().
- services/tool-runner.js delegates to tools/index.js executeTool(), now guarded by the shared tool policy.
- services/mira-verification-engine.js directly invokes tool_health.execute(); this is a read-only inspection tool.
- autonomous-learning-controlled-apply.js directly calls knowledge.addLearning() only after an approved proposal is found. routes/autonomous-learning.js mounts this under requireSystemAdmin; the route and controlled-apply service both recheck approved status. The service creates and verifies a snapshot before the local apply and retains its rollback/reconciliation path. This is a separately approved controlled-apply workflow, not the learning_save tool wrapper.
- server.js calls addMemory() to persist ordinary user/assistant conversation transcript records. This is a system conversation-persistence path, distinct from the model-callable memory_save wrapper.

No direct server import of memory-save, knowledge-save, or learning-save was found in the reviewed server/route sources.

6. RESIDUAL GAPS — NOT CLOSED

- The raw tools object remains exported and individual tool modules can still be imported and invoked directly. The reviewed direct callsites have separate guards or are read-only, but a repository-wide proof that no other dynamic import/direct execute() path exists has not been established.
- The dedicated admin backup/restore and SEO dispatch paths are not unified under one authenticated action-scoped approval-token contract. Their current route/session/permission gates were source-reviewed and regression-checked, not certified as a universal approval protocol.
- The autonomous-learning controlled-apply workflow uses approved proposal status and SYSTEM_ADMIN route permission, but the broader provenance/custody/anti-replay properties of that approval remain separate governance qualification work.
- The static parity test recognizes the current export patterns; a new export style or dynamic name expression requires manual test/parser review.
- Production Memory/Knowledge read/write integration, all provider adapters, all workers and every dynamically loaded application module have not been exhaustively runtime-tested.

Required next work:
1. Continue repository-wide direct execution/import callsite reconciliation, including all service modules and background entry points.
2. Review whether the raw tools object should be replaced with a guarded facade while preserving dedicated authenticated admin dispatch behavior.
3. Define a single action-scoped authenticated approval contract for dedicated admin write routes; do not treat generic permissionGranted=true or model arguments as approval.
4. Add route-level isolated tests for backup/restore authorization and controlled-learning apply, with all storage/provider calls stubbed.
5. Keep memory_save, knowledge_save and learning_save human-only until approval authority is implemented and independently verified.
