1. PURPOSE

Assess the remaining gap between the current local quarantine primitives/read-only conflict classifier and the complete conflict lifecycle required by the v0.2.4 contract Section 5. This is a source inspection only. No production data was accessed and no code was changed by this assessment.

3. VERIFIED CURRENT BEHAVIOR

A. Local quarantine primitive
services/mira-json-state-store.js provides quarantineConflict(directory, name, payload, metadata):
- Creates a project-local memory-conflicts directory.
- Rejects a symlink or non-directory quarantine path.
- Writes a timestamped JSON envelope with quarantineVersion, quarantinedAt, reason, metadata and payload.
- Uses the shared atomic writer and records a memory_conflict_quarantined audit event.
- Returns the quarantine file path and SHA-256 digest.
- If audit recording fails after the quarantine write, throws with stateCommitted=true.

B. Knowledge capacity eviction
knowledge.js preserves capacity-evicted records in local quarantine before committing the bounded active Knowledge set. The normal Knowledge search path loads the active Knowledge state; the quarantine directory is not included in the ordinary search result set.

C. Evolution divergence
knowledge-memory-evolution.js detects Local/Drive divergence and reconciliation-proposal mismatch, attempts to preserve the competing states/proposal in quarantine, and blocks the operation. Quarantine write failure is returned as conflict_quarantine_failed.

D. Structural assessment
services/mira-memory-conflict-assessment.js validates canonical record structure and classifies the seven contract conflict categories. It is read-only and explicitly reports cryptographicVerification=NOT_PERFORMED.

4. REMAINING LIFECYCLE GAPS

CLG-01 — Durable conflict identity and envelope contract: REVIEW_REQUIRED
The generic quarantine envelope does not yet define a canonical conflictId, sourceRecordIds, per-version schema/profile identifiers, immutable original version references, conflict state, resolution state or a stable correlation ID. The Evolution payload preserves local/Drive/proposal objects, but it is not yet a canonical reusable conflict record.

CLG-02 — Quarantine read/list/verify API: REVIEW_REQUIRED
The inspected state-store exports a quarantine write helper but no dedicated list, read, verify, status-transition or retention API for conflict records was identified in the inspected module.

CLG-03 — Trusted retrieval exclusion: REVIEW_REQUIRED
The Knowledge active search path naturally excludes files stored only in its separate quarantine directory. However, no repository-wide quarantine registry or shared retrieval guard was found in the inspected call paths to enforce exclusion for every provider, adapter, cache, search and Evolution retrieval path. This must not be inferred from the local Knowledge behavior.

CLG-04 — Governed resolution workflow: REVIEW_REQUIRED
No complete resolution workflow was found that preserves both originals, records merge/reject decision, actor, policy decision, resulting revision, source provenance and audit correlation while preventing silent last-write-wins.

CLG-05 — Write-boundary integration: REVIEW_REQUIRED
The structural assessor is not demonstrated to be invoked at every provider/adaptor write boundary. No universal guarantee exists yet that all incoming writes are validated and conflict-checked before commit.

CLG-06 — Cryptographic content verification: NOT_PERFORMED
The structural assessor checks contentHash shape only. It does not recompute contentHash from an approved canonical serialization profile. No cryptographic verification claim is made.

CLG-07 — Concurrent arbitration and uncertain writes: REVIEW_REQUIRED
No chain-level authoritative append-arbitration or provider-native compare-and-swap qualification is established by these local primitives.

CLG-08 — Independent evidence verification: REVIEW_REQUIRED
No independent verifier qualification is established. The existing audit stream and quarantine SHA-256 are not substitutes for E-15.

5. REQUIRED SAFE IMPLEMENTATION ORDER AFTER APPROVAL

1. Approve a canonical conflict record schema and immutable original-version reference model.
2. Define quarantine state transitions and access policy.
3. Implement isolated list/read/verify APIs over synthetic fixtures only.
4. Prove trusted retrieval excludes quarantined IDs across every registered retrieval entry point.
5. Define governed merge/reject resolution with immutable source preservation and audit correlation.
6. Integrate pre-write validation at each approved adapter boundary.
7. Add concurrency, uncertain-write and replay tests.
8. Qualify independent evidence verification.
9. Only after separate migration/production authorization, consider production adapters or data.

6. TEST REQUIREMENTS

- Both original versions survive every conflict transition unchanged.
- Quarantine write failure blocks the parent operation.
- Quarantined record is never returned by trusted retrieval.
- Cross-project access is denied.
- Duplicate conflict IDs are idempotent only for identical payload; differing payload is CONFLICT.
- Invalid state transitions are rejected.
- Resolution requires authorized actor and policy decision.
- Resolution output references both originals and increments revision exactly once.
- Audit failure prevents resolution from reporting success.
- Hash verification uses a frozen canonical profile and independent test vectors.
- All tests use synthetic fixtures and record productionDataTouched=NO and networkRequests=0.

## 8. Follow-up repository retrieval-path audit (2026-11-04)

The following concrete paths were inspected after the initial assessment:

1. knowledge.js
   - searchKnowledge() (around lines 860 onward) reads only loadKnowledge(), which reads the configured active knowledge.json through mira-json-state-store.readJsonArray.
   - getKnowledge() likewise returns the active canonical local Knowledge array.
   - This path does not enumerate or read the separate memory-conflicts quarantine directory. This is a useful local retrieval boundary, but it is not proof that every caller/provider uses this path.

2. tools/knowledge-search.js
   - Starts with getKnowledge() from local Knowledge.
   - Then calls loadKnowledgeFromDrive() and replaces the local candidate set with the returned Drive array whenever that is an array.
   - Therefore the tool has a separate provider-backed retrieval path that is not governed by the local knowledge.js reader. It is part of the HFM-004 Drive/provider boundary and is NOT changed here because Drive cutover/provider migration is not authorized.
   - No live Drive request was made during this source inspection.

3. knowledge-memory-evolution.js
   - Uses local Memory/Knowledge plus Drive load/save adapters for reconciliation and Evolution.
   - Its mismatch path can quarantine payloads, but no repository-wide evidence yet establishes that all subsequent Evolution/retrieval consumers exclude quarantined or unresolved source versions.

4. services/mira-experience-retrieval-engine.js
   - Retrieves from the separate mira-experience-memory subsystem through listExperiences().
   - It is not the canonical memory.json or knowledge.json reader and has not been demonstrated to consume the conflict registry's resolution state.

5. services/mira-conversation-memory-engine.js
   - Uses the separate conversation-store subsystem. Its relationship to conflict quarantine, trust state and project-scoped retrieval has not yet been proven by the current audit.

### Updated retrieval-boundary status

- Canonical local Knowledge active-state retrieval via knowledge.js: SOURCE_INSPECTED; quarantine directory is not read by that module.
- Tool-level Knowledge retrieval with Drive override: REVIEW_REQUIRED; distinct provider path exists and remains under HFM-004 authorization boundary.
- Memory, conversation, experience, Evolution, cache and provider-wide exclusion: REVIEW_REQUIRED; full call-graph and runtime regression evidence are still missing.
- No source changes, production data reads, Drive calls, network requests or external actions were performed for this read-only audit.

This narrows the earlier broad gap: a local canonical path exists, but universal trusted retrieval exclusion cannot be claimed until every alternate retrieval adapter and provider/cache path is mapped and tested.
