2. IMPLEMENTED SOURCE CHANGES

A. Shared JSON state-store primitives
Path: services/mira-json-state-store.js
- Strict JSON-array read with explicit first-run missing-file behavior.
- Rejects empty, malformed, non-array, symlink, and non-regular-file state.
- Atomic temporary-file write with exclusive creation, restrictive file mode, fsync, rename, and independent SHA-256 readback.
- Writes an immutable pre-write version snapshot before replacing an existing valid array.
- Provides a local conflict-quarantine envelope with SHA-256 evidence and source metadata.

B. General Memory
Path: services/mira-local-memory-store.js
- Missing primary Memory file falls back to a validated local backup when one exists; the backup is not silently written over the primary during read.
- Missing primary with no backup remains a first-run empty state.
- Corrupt, empty, unreadable, non-array, or unsafe primary state fails closed.
- Normal writes use the shared atomic/versioned state writer.
- Explicit restore validates the backup first and requires the existing tool confirmation.
- Before restoring over corrupt primary data, exact original bytes are preserved in a separate quarantine file with SHA-256 evidence.
- Restore then performs atomic replacement and readback verification.

C. Knowledge
Path: knowledge.js
- A missing Knowledge file remains a first-run empty state.
- Existing malformed, empty, unreadable, non-array, or unsafe Knowledge state now throws instead of silently becoming [].
- Knowledge CRUD writes use the shared atomic/versioned state writer.
- Capacity overflow no longer silently drops older entries: displaced records are preserved in a restricted local conflict-quarantine envelope before the bounded Knowledge state is committed.
- Knowledge backup is local, versioned, SHA-256 verified and offline. A corrupt existing backup is preserved and blocks overwrite.
- Knowledge restore requires explicit confirmation, validates the backup, creates a safety backup or preserves corrupt primary bytes verbatim, performs atomic restore/readback, and records audit events.
- The legacy Knowledge restore tool no longer falls back to Google Drive or writes directly with fs.writeFileSync; it is local-only. This is not the encrypted emergency backup required by HFM-005.

D. Evolution integration
Path: knowledge-memory-evolution.js
- Memory Evolution reads through the shared Local Memory Store.
- Memory Evolution writes through the shared Local Memory Store; Knowledge Evolution writes through the shared JSON state store.
- Split Memory storage roots fail closed.
- Evolution refuses to snapshot/apply when its target path is outside the Snapshot Manager's safe project-relative boundary.
- Local/Drive divergence is preserved in a local conflict quarantine record and apply is blocked; reconciliation proposal mismatch is also quarantined.
- Existing snapshot, approval, preservation, Drive verification, and rollback flows remain in place.

14. EXPLICIT VERSION SELECTION AND ACCESS-CHANGE AUTHORIZATION — VERIFIED BY RUN 303

Further review found two Section 30 governance ambiguities in the isolated resolver:
- Original array order was being treated as the implicit meaning of "existing" or "rejected change". The resolver now requires an explicit acceptedOriginalIndex for ACCEPT_EXISTING_VERSION and REJECT_CONFLICTING_CHANGE, and verifies the exact selected original digest. ACCEPT_ALTERNATE_VERSION also requires an explicit valid index.
- Any change to the merged record's access policy is treated conservatively as a policy change. It requires a separate authorizeBroaderAccess callback to return true and a non-empty broaderAccessAuthorization evidence reference. 18. CANONICAL CONTENT-HASH RECOMPUTATION IN CONFLICT ASSESSMENT — VERIFIED BY RUN 344

Contract v0.2.4 Section 8.4 defines the record content hash as SHA-256(UTF-8(JCS(content))). The prior structural assessor checked only that contentHash was a 64-character hexadecimal string; a changed content string paired with an arbitrary well-shaped hash could pass structural validation.

Correction:
- services/mira-memory-conflict-assessment.js now recomputes SHA-256 over the RFC 8785 canonical JSON serialization of the content string (JSON.stringify for this string primitive) and rejects mismatches.
