1. PURPOSE AND METHOD

This review interprets the read/retrieval callsites emitted by tests/mira-hfm-retrieval-callsite-inventory.test.js. The scanner found 36 retrieval calls across 14 application source files. All 14 consumer files lack both an in-file filterTrustedRecords marker and a recognized conflict-quarantine filter marker.

This is a static source inventory and semantic classification. A missing marker is a review lead, not proof that a specific production record was returned or exposed. The scanner does not resolve all imports, wrappers, aliases, dynamic dispatch, runtime reachability or filters applied in another module.

No production Memory/Knowledge data was read or modified. No real Drive, provider, network or external action was performed.

3. KEY ARCHITECTURAL BLOCKER

The legacy Memory and Knowledge shapes do not universally carry the canonical fields needed for a safe runtime filter:
- Conversation Memory legacy records lack persisted immutable messageId in all historical cases and Conversation schema lacks projectId.
- Legacy Knowledge records do not universally carry explicit canonical projectId, memoryId, revision, source digest, classification, approval reference and trust state.
- The read-only legacy adapter intentionally requires explicit source-bound mapping; it does not invent messageId/projectId or derive project scope from opportunityId.
- A generic filter cannot safely manufacture missing identity or trust metadata.

Therefore, immediately wiring filterTrustedRecords() to every legacy read without an explicit mapping plan would either (a) silently exclude most legacy data, or (b) tempt callers to synthesize missing identity/trust fields. Neither is an approved migration.

4. RECOMMENDED SAFE REMEDIATION SEQUENCE

1. Define one canonical retrieval facade that requires an authenticated explicit projectId and a source-bound mapping for every legacy record.
2. Require canonical record validation, content-hash consistency, lifecycle ACTIVE, integrity VERIFIED, allowed explicit trust state and conflict-quarantine exclusion before returning any content.
3. Treat missing projectId, immutable messageId, revision, mapping approval, trust state or quarantine status as excluded / REVIEW_REQUIRED. Never derive projectId from opportunityId alone.
4. Make local and Drive retrieval use the same canonical facade. A Drive array must never replace a local search corpus before canonical filtering.
5. Integrate first at the highest-risk model-context boundary in server.js, then tools/knowledge-search.js, services/learning.js, admin search/detail, and the remaining read consumers.
6. Keep admin role checks in addition to HFM project/trust filters; do not treat admin role as a data-scope waiver.
7. Keep raw counts explicitly labelled RAW_LOCAL_COUNT until trusted-count semantics are implemented.
8. Keep controlled apply/recovery/sync reads on a separately reviewed provider-arbitration path; do not mix ordinary retrieval filters with recovery snapshots without a defined recovery policy.
9. Add integration tests with cross-project, missing-mapping, pending-review, quarantined, malformed, integrity-failed and allowed trusted fixtures. Prove excluded content never enters the model prompt or tool output.
