1. EXECUTIVE RESULT

HFM-005 is NOT IMPLEMENTED and remains NOT_AUTHORIZED. The current local backup mechanisms provide useful integrity and recovery safeguards, but they do not provide encryption or authenticity. A SHA-256 digest detects accidental or unauthorized byte changes only when the expected digest itself is trusted; it does not prove who created the backup or protect confidentiality.

No encryption, key generation, key storage, key export, credential access, production backup, restore, provider access or network action was performed.

2. SOURCE EVIDENCE

- Backup format version 2 stores entries, entryCount, source, createdAt and SHA-256 over canonicalized entry JSON.

C. tools/knowledge-backup.js and tools/knowledge-restore.js

4. REQUIRED DESIGN DECISIONS BEFORE IMPLEMENTATION

A. Threat model and confidentiality boundary
- Define whether emergency backups protect against device loss, filesystem theft, app compromise, malicious local user, repository compromise, or provider compromise.
- Define plaintext-at-rest and temporary-file handling requirements.
- Define which fields may be included and whether metadata itself is sensitive.

B. Cryptographic construction
- Select an authenticated encryption construction and approved library/runtime support.
- Specify nonce generation, uniqueness, associated authenticated data, format versioning and algorithm agility.
- Define whether manifest authenticity uses a signature or a MAC; do not treat payload SHA-256 as authenticity.
- Define canonical serialization and exact bytes covered by each digest/tag/signature.

C. Key lifecycle and recovery
- Define key generation, entropy source, custody, access control, rotation, revocation, backup and recovery.
- Separate decryption/authentication trust material from the encrypted payload.
- Define device-loss recovery without plaintext fallback or silent key regeneration.
- Define what happens when keys are missing, revoked, corrupted or unavailable.
- Do not store keys beside ciphertext or in repository source/config.

D. Restore gate
- Verify envelope/manifest authenticity before decrypting or writing.
- Verify ciphertext integrity/authentication, format, project scope, schema, access classification and key status.
- Prepare a verified recovery point; require explicit approval; restore only approved scope.
- Independently read back and verify identities, revisions, counts, hashes and access boundaries.
- Any failed/uncertain step must block COMPLETED status.

E. Operational and compatibility requirements
- Define migration behavior for existing plaintext backups without silently converting or deleting originals.
- Define storage location, file permissions, atomic replacement, crash recovery and retention.
- Define a reproducible test harness with synthetic keys and fixtures only.
- Include tamper, wrong-key, missing-key, revoked-key, nonce, rollback, cross-project, truncation, partial-write and restore-interruption tests.
- Require independent security review before production use.
