2. ADDITIONAL FINDINGS
A. Google Drive provider boundary — google-drive.js
- saveKnowledgeToDrive() at lines 201–218 writes the supplied Knowledge array through Drive helpers.
- loadKnowledgeFromDrive() at lines 220–234 returns Drive Knowledge without canonical project mapping or conflict-registry filtering at this boundary.
- saveMemoryToDrive()/loadMemoryFromDrive() at lines 236–269 are distinct Memory provider boundaries.
- Existing Phase 1 authority policy says Drive sync must not be cut over or removed without separate approval. Phase 2 must not make live Drive calls in CI.
Finding: provider boundary needs normalization, project-scope verification, quarantine filtering and write arbitration before remote calls. Existing offline CI stub is retained.

B. Knowledge cleanup tool — tools/knowledge-cleanup.js
- inspectKnowledge() reads getKnowledge() at line 53.
- removeDuplicates() reads getKnowledge() at line 81, calls replaceKnowledge() at line 100, then saveKnowledgeToDrive() at line 103.
- It uses title/url/content equality, not canonical identity/revision/conflict arbitration.
Finding: this is a direct destructive rewrite + provider sync path. It must be registered as a governed write boundary; duplicate similarity must not erase conflicting versions or forensic originals. No production execution was performed.

C. Knowledge improvement proposals — knowledge-improvement.js
- Proposal state reads through jsonStateStore.readJsonArray() at lines 11–17.
- saveProposals() writes atomically and audits at lines 19–45.
Finding: proposal records are not canonical Knowledge records, but controlled-apply must preserve proposal-to-source linkage and cannot bypass Knowledge write arbitration.

D. Autonomous learning / general learning — services/learning.js and routes/autonomous-learning.js
- services/learning.js calls addLearning() at line 479 and updateLearning() at line 645.
- routes/autonomous-learning.js imports autonomous learning engine/proposal/controlled-apply services.
Finding: these are indirect Knowledge mutation callers; they inherit the knowledge.js boundary and must be included in the caller registry and integration tests.

E. Stage 13 Learning Governance — services/mira-stage13-learning-governance.js
- Own JSON store path is selected at lines 11–12.
- ensureStore()/loadStore()/saveStore() perform independent persistence at lines 43–69.
- persist() appends records and events at lines 99–104.
- Feedback, failure and benchmark records are persisted by recordFeedback()/recordFailure()/recordBenchmark() at lines 145–214.
Finding: this is a separate governance/learning evidence domain, not general Memory or canonical Knowledge. It needs data classification, project/source linkage and integrity/retention policy; do not silently merge it into Knowledge.

F. Work Knowledge Consolidation — services/mira-work-knowledge-consolidation.js
- loadStore() validates a separate items store at lines 141–178.
- saveStore() uses atomicWriteJson() and state audit at lines 180–205.
- getConsolidatedKnowledge() reads items at line 919; stats reads them at lines 923–930.
Finding: distinct derived/proposal store. Its current fail-closed storage tests do not establish canonical conflict-registry filtering or project-scoped retrieval.

G. Work Learning — services/mira-work-learning-engine.js
- loadStore() reads a separate records store at lines 192–228.
- saveStore() validates and writes the records collection from line 235 onward.
- services/learning.js and quality handoff call this engine.
Finding: separate learning domain; existing fail-closed store tests do not prove canonical HFM project isolation or quarantine filtering.

H. CRM Conversation response path
- services/mira-conversation-response-planner.js reads getConversationMemory() at lines 185–188.
- routes/conversations.js creates structured messages and updates conversation memory at lines 245–267; its memory endpoint reads getConversationMemory() at lines 445–465.
Finding: the CRM response planner consumes CRM conversation context. A project mapping cannot be inferred from messageId or clientId; an approved conversation-to-project registry is still required.

I. Memory backup script
- scripts/mira-memory-backup.js delegates to local memory store createBackup().
Finding: backup/restore and user export are separate policy boundaries. Backups may preserve forensic originals; normal retrieval/export must apply quarantine policy. No backup was run.

J. Other research/provider/governance routes
- Provider evolution routes maintain separate runtime/staging/rollback configuration state.
- Research governance, SEO research and learning history have separate evidence/history stores and should be classified independently.
Finding: not every store named "memory" or "learning" is the canonical HFM Memory domain. The boundary inventory must retain domain labels rather than forcing a single adapter over every file.

5. PHASE 2 PROGRESS — NEW DRY-RUN MANIFEST PLANNER
Added:
- services/mira-hfm-migration-manifest.js
- tests/mira-hfm-migration-manifest.test.js
- CI workflow now executes the isolated planner suite.

Planner behavior:
- Accepts exact source JSON snapshot text and computes its SHA-256 digest.
- Requires a JSON array and non-negative source ordinals.
- Uses domain-specific identity extraction for General Memory, Knowledge and CRM Conversation messages.
- Requires explicit legacy ID, canonical memoryId, projectId, revision 1, source digest, classification and approval reference.
- Verifies CRM message's parent conversation identity.
- Rejects duplicate/unused mappings, stale source digest, invalid snapshot JSON, missing immutable Memory ID, unknown classification and canonical ID collisions.
- Emits BLOCKED or READY_FOR_REVIEW only. Every candidate and plan has writeAuthorized=false.
- Does not read/write local files, production data, Drive or providers.
- The source digest algorithm was aligned with the existing read-only adapter and tested for compatibility.
