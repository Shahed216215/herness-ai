3. LOCAL MEMORY CALL PATH

A. Retrieval
- memory.js loadMemory() delegates to localStore.readMemory().
- memory.js getMemory() returns loadMemory().
- services/mira-local-memory-store.js readMemory() reads the primary Memory JSON array; if missing, it may return entries from a verified backup; if neither exists it returns [].
- The inspected readMemory path does not consult the conflict registry or structural conflict assessor.

B. Writes
- memory.js saveMemory() validates array shape, applies capacity slicing, then calls localStore.writeMemory().
- memory.js addMemory() loads the current array, checks duplicate role/content, appends a message with Date.toISOString(), and saves.
- services/mira-local-memory-store.js writeMemory() delegates to jsonStateStore.writeArrayState().
- The inspected write path does not call assessMemoryConflict(), createConflictQuarantine(), or a registry authorization/resolution gate.

C. Data-model boundary
The current conversation Memory array stores message-like objects (role/content/time). It is not the canonical Memory record schema validated by mira-memory-conflict-assessment.js. Applying that canonical validator directly to this legacy message array would reject valid current records and is not safe without a separately approved schema/adapter design.

4. LOCAL KNOWLEDGE CALL PATH

A. Retrieval
- knowledge.js loadKnowledge() reads the active Knowledge JSON array using jsonStateStore.readJsonArray().
- searchKnowledge(), getKnowledge() and getKnowledgeStats() all call loadKnowledge().
- The inspected active Knowledge retrieval path does not consult the new conflict registry or structural conflict assessor.

B. Writes
- addKnowledge() loads active Knowledge, checks duplicate title/content/URL semantics, and later persists/synchronizes the updated array.
- addLearning() validates learning input, loads active Knowledge and checks duplicate title/topic/content.
- updateKnowledge(), updateLearning() and deleteKnowledge() load active Knowledge, locate an entry and write the updated array.
- saveLocalKnowledge() delegates to jsonStateStore.writeArrayState().
- The inspected add/update/delete paths do not invoke assessMemoryConflict() or the new registry's governed resolution API at a universal pre-write boundary.

C. Existing capacity quarantine is distinct
applyKnowledgeCapacity() calls jsonStateStore.quarantineConflict() to preserve capacity-evicted entries before committing the bounded active set. That legacy envelope is not the new canonical conflict registry envelope; it has no guaranteed canonical conflictId, source-version pair, governed resolution record or registry status. It must not be silently treated as equivalent.

5. REGISTRY INTEGRATION STATUS

The isolated registry exposes:
- createConflictQuarantine()
- readConflict()
- verifyConflict()
- listConflicts()
- resolveConflict()
- verifyResolution()
- filterTrustedRecords()

The filter is a pure helper that requires the caller to supply the relevant conflict list. It is not a global interception layer. The registry does not currently wrap memory.js, localStore.readMemory(), knowledge.js loadKnowledge(), searchKnowledge(), getKnowledge(), or the add/update/delete write paths.

6. REQUIRED INTEGRATION PLAN — NOT IMPLEMENTED

Before runtime integration, define separate adapters for the existing conversation-message Memory model and canonical Knowledge record model. Do not force both through one schema.

Proposed order:
1. Inventory every public API, route, worker, tool, background task and direct file reader that can retrieve or mutate Memory/Knowledge.
2. Define per-domain record identity and conflict mapping without changing existing records.
3. Define how legacy capacity/divergence quarantine envelopes are imported or remain separate.
4. Build one policy-aware retrieval guard and prove all public retrieval entry points use it.
5. Add pre-write validation and conflict arbitration to each authorized write boundary.
6. Prove quarantined items are excluded from search, list, count, snippets, export, backup and restore according to policy.
7. Test cross-project isolation, cache/index invalidation, concurrent writes, audit failure and recovery using synthetic fixtures.
8. Only after independent review and explicit scope approval, propose any production data migration or provider integration.

10. SEMANTIC CALLSITE REVIEW — 2026-11-04
The following source ranges were fetched from the Phase 2 branch and manually classified. These are direct observations of the current branch source, not assumptions from regex matches.

A. Conversation persistence and retrieval
- conversation-store.js:13-42 validateStore()/ensureStore(): creates/validates the conversations.json envelope and initializes empty conversations/messages/contexts. It does not assign a projectId to each message.
- conversation-store.js:300-370 createStoredMessage(): validates parent conversation existence, rejects duplicate messageId, appends message and increments parent messageCount, then persists via saveStore(). This is a direct message write boundary.
- conversation-store.js:390-460 getContext()/saveContext(): contexts are keyed by conversationId; saveContext merges and persists without a canonical HFM projectId/revision mapping or conflict-registry arbitration.
- services/mira-conversation-memory-engine.js:155-169 getConversationHistory(): retrieves all messages for a conversation and returns messageId/participant/direction/status/content/createdAt.
- services/mira-conversation-memory-engine.js:283-357 updateConversationMemory(): derives context from a supplied message and writes context through store.saveContext(). This is a second write path, distinct from message persistence.
- services/mira-conversation-memory-engine.js:364-399 getConversationMemory(): returns parent conversation, stored context and full history. No conflict quarantine registry call is present in this retrieval path.
- routes/conversations.js:240-285 incoming message route calls createConversationMessage() then updateConversationMemory(); the two persistence operations are sequential rather than one transaction. A failure after message commit can leave message/history and derived context out of sync.
- routes/conversations.js:445-485 GET conversation memory calls getConversationMemory() directly after conversation existence check; it does not apply canonical HFM trusted-record filtering.
Conclusion: conversation message storage has immutable messageId at the schema/store boundary for new messages, but existing legacy messages may lack it; the context record has conversationId but no independently approved projectId mapping. The isolated sidecar adapter must remain opt-in/read-only until identity and project mapping are established for every legacy record.

B. Knowledge persistence and retrieval
- knowledge.js:150-240 addKnowledge(): loads the complete local Knowledge array, creates an ID, appends and writes the array; duplicate detection is semantic rather than canonical source-version arbitration.
- knowledge.js:700-820 updateLearning(): locates an existing item by ID or normalized title, replaces selected fields, writes the array and invokes Drive synchronization. This is a direct local write boundary followed by a provider sync attempt.
- knowledge.js:820-900 searchKnowledge(): calls loadKnowledge(), tokenizes the query and ranks entries; no conflict registry or canonical trust-state filter is called in the inspected search path.
- knowledge.js:900-980 getKnowledge()/getKnowledgeStats(): reads the active array directly; no canonical quarantine filter is called in the inspected list/stat path.
- services/mira-knowledge-state-recovery.js:110-143 createKnowledgeBackup(): reads the entire Knowledge array and writes a backup envelope. It does not currently filter pending/quarantined canonical records by HFM policy.
- services/mira-knowledge-state-recovery.js:146-220 restoreKnowledge(): after explicit confirm, validates backup, preserves a safety copy/quarantine, writes the restored entries and verifies readback. This is a destructive state-replacement boundary; HFM quarantine policy is not integrated into restore eligibility.
Conclusion: Knowledge still uses a legacy array model with per-entry IDs, no universally enforced projectId/revision, and local+Drive synchronization. The HFM adapter is not wired into these paths. Backup/restore and Drive synchronization require separate explicit policy integration and dedicated tests.

C. Local Memory persistence and recovery
- services/mira-local-memory-store.js:19-63 readArray(): rejects symlink/non-file, empty or invalid JSON and non-array payloads.
- services/mira-local-memory-store.js:74-140 atomicWriteJson(): temp-file exclusive create, fsync, chmod, rename, directory fsync best-effort and readback hash verification.
- services/mira-local-memory-store.js:143 onward readMemory(): reads the primary Memory array; on missing primary it can expose a verified backup read-only and avoids turning a missing primary into an empty write.
- services/mira-local-memory-store.js exports createBackup()/restoreMemory(); those paths remain separate from HFM conflict-registry retrieval and write arbitration.
Conclusion: local store has meaningful filesystem integrity controls, but they are not equivalent to HFM identity, trust, project-scope or conflict-resolution controls.

D. Route and cross-domain boundary implications
- Conversation routes and Knowledge routes are separate call paths; no single shared guard currently intercepts both.
- Knowledge add/update/delete, conversation message create, conversation context save, Knowledge search/list, conversation history/context retrieval, backup and restore each need an explicit integration decision and a dedicated test.
- A route-level authentication/authorization check does not establish canonical record integrity, project isolation, trusted provenance or conflict arbitration.
- A regex inventory match is not counted as a semantic HFM boundary unless the inspected source establishes that role. The broader 1125-match inventory remains a review index, not 1125 confirmed HFM operations.

12. IDENTITY SCHEMA AND FAILURE-ATOMICITY FINDINGS — 2026-11-04
- conversation-schema.js:123-178 createConversation() persists clientId, opportunityId and proposalId but has no projectId field. The schema therefore cannot itself prove conversationId -> projectId.
- conversation-schema.js:181-228 createConversationMessage() creates a messageId when absent for new messages and stores conversationId/clientId, but no projectId. This does not retroactively provide immutable IDs to legacy records that were already persisted without them.
- routes/conversations.js:240-285 performs message creation and context update as separate calls. The message store commit precedes derived context update; if the latter fails, the endpoint can return an error while the message has already been persisted. No transaction/outbox/compensating rollback was found in the inspected path. Treat as a consistency/recovery gap, not as a confirmed data-loss incident.
- knowledge.js:150-240 and 700-820 perform local array writes before/around asynchronous Drive synchronization. A provider failure can leave local and remote state divergent; the current path needs explicit idempotency/version arbitration and reconciliation evidence before it can be considered a single authoritative write boundary.
