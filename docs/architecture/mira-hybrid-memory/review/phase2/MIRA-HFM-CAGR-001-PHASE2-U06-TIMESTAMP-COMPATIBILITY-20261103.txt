1. PURPOSE

Assess whether the accepted U06 planning direction (versioned, deterministic UTC timestamp representation with fixed precision and explicit rejection rules) conflicts with the currently inspected audit and Memory record code. This is a source review only. No timestamp runtime behavior was changed.

3. OBSERVED CURRENT BEHAVIOR

A. Existing audit-log timestamp generation
audit-log.js creates new audit entries with:
timestamp: new Date().toISOString()
The integrity payload includes entry.timestamp, and the current legacy hash function serializes the payload with JSON.stringify before SHA-256 hashing.

For timestamps generated by this code path, JavaScript Date.toISOString() emits UTC with exactly millisecond precision and uppercase T/Z. This aligns with the proposed canonical spelling for newly created audit events.

B. Memory record structural validator
services/mira-memory-conflict-assessment.js validates source.observedAt, timestamps.createdAt and timestamps.updatedAt as RFC 3339-shaped date-time strings. It currently accepts:
- UTC Z or explicit numeric offsets;
- upper/lowercase T and Z;
- zero or variable fractional-second precision;
- leap-second second value 60.

It validates calendar day/month and offset bounds, but does not normalize values to UTC or require exactly three fractional digits. This is structural validation, not canonical serialization or hash verification.

C. Local quarantine/version timestamps
services/mira-json-state-store.js and services/mira-conflict-quarantine-registry.js generate new createdAt/quarantinedAt/resolvedAt values using Date.toISOString(), so new local records use UTC millisecond precision. Existing input records remain governed by the separate Memory record validator.

D. Contract evidence
The contract-v024-vs-prototype-e-core-evidence §10.2 explicitly leaves final timestamp precision and serialization unresolved and requires a selected profile to define UTC normalization, offset handling, precision, fractional behavior, leap seconds, invalid timestamps and missing timestamps.

4. COMPATIBILITY FINDINGS

U06-COMP-01 — Existing audit-log emission is profile-compatible for newly generated timestamps: PASS_SCOPED_SOURCE_INSPECTION.
Date.toISOString() already emits the proposed UTC millisecond form. This does not prove historical log entries all conform or independently verify them.

U06-COMP-02 — Existing Memory record validator is broader than the proposed canonical audit-chain profile: PASS_SCOPED_SOURCE_INSPECTION.
It accepts offset-bearing and variable-precision timestamps. Do not silently tighten it as part of U06 without a separate Memory schema migration/compatibility review.

U06-COMP-03 — Audit hash input binds the timestamp string as stored: PASS_SCOPED_SOURCE_INSPECTION.
Because timestamp is included in JSON.stringify payload before hashing, alternate representations of the same instant produce different hash inputs. Canonicalization must therefore occur before append/hash, not only during display or verification.

U06-COMP-04 — Leap-second and excess-precision policy are not implemented as a single chain profile: REVIEW_REQUIRED.
The Memory validator permits second=60 and variable precision; audit-log Date generation avoids such inputs but no canonical chain validator is established.

5. PROPOSED U06 PROFILE FOR OWNER REVIEW

Profile identifier: MIRA-HFM-TIMESTAMP-RFC3339-UTC-MS-v1

Canonical serialized form:
YYYY-MM-DDTHH:mm:ss.sssZ

Proposed rules:
1. Canonical bytes contain UTC only, uppercase T/Z and exactly three fractional digits.
2. Input must contain a full RFC 3339 date-time and explicit timezone.
3. Validate calendar date and offset before normalization.
4. Valid offset-bearing input may be normalized to UTC before canonical serialization.
5. Reject precision beyond milliseconds; never silently round or truncate.
6. Reject leap seconds until an explicit compatible representation is approved.
7. Reject missing timezone, date-only input, invalid calendar date and invalid offset.
8. Keep eventCreatedAt and providerObservedAt semantically distinct; do not overload one field.
9. Timestamp is event metadata, not proof of trusted wall-clock time or causal ordering.
10. Sequence number, not timestamp, determines chain order.
11. Bind profile identifier/version into the canonical event/hash profile.
12. Display formatting must never alter canonical hash input.

6. REQUIRED TEST VECTORS

- UTC input at exactly millisecond precision is accepted unchanged.
- Equivalent offset inputs normalize to identical UTC canonical bytes.
- Date-only and timezone-free inputs are rejected.
- Invalid month/day/leap-day and invalid offset are rejected.
- More than three fractional digits are rejected.
- Leap-second input is rejected under v1.
- Same canonical event serialized by independent implementations yields identical bytes and digest.
- Changing the profile version changes the declared profile context and requires explicit migration rules.
