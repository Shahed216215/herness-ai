2. ADDITIONAL STORAGE ROOT FINDINGS

2.1 Storage-root aligned components (confirmed in inspected source)
- memory.js delegates to services/mira-local-memory-store.js.
- services/mira-local-memory-store.js defaults to storagePath('memory.json'), but MIRA_MEMORY_FILE can override it with path.resolve(...). The override is an independent absolute-path configuration and is not automatically constrained to MIRA_STORAGE_DIR by the inspected code.
- services/mira-work-learning-engine.js uses storagePath('data/work-learning-records.json').
- services/mira-work-knowledge-consolidation.js uses storagePath('data') then appends work-knowledge-consolidation.json.
- services/mira-stage13-learning-governance.js uses storagePath('data/stage13-learning-governance.json').
- conversation-store.js uses storagePath('data/conversations.json').
- knowledge-improvement.js and autonomous-learning-proposals.js use storagePath for their proposal files.
- audit-log.js uses MIRA_AUDIT_FILE when configured, otherwise storagePath('audit-log.json'). This is another independent absolute-path override.

2.2 Snapshot storage divergence (confirmed)
snapshot-manager.js sets SNAPSHOT_ROOT to PROJECT_ROOT/backups/changes and does not import mira-storage in the inspected header. This means snapshots remain project-root scoped even when MIRA_STORAGE_DIR points elsewhere. This may be an intentional project artifact boundary, but it is not a unified storage root. Any migration design must distinguish user Memory/Knowledge persistence from code-change recovery snapshots and explicitly document whether snapshots should remain project-local.

2.3 Independent path overrides
- MIRA_MEMORY_FILE can override Memory storage independently of MIRA_STORAGE_DIR.
- MIRA_AUDIT_FILE can override audit storage independently of MIRA_STORAGE_DIR.
These overrides may be intentional deployment controls; their precedence, allowed roots, permissions, and backup/recovery semantics need a configuration contract. No environment values or live data were read.

2.4 Legacy Knowledge tools (reconfirmed)
- knowledge-cleanup, knowledge-backup, knowledge-restore construct project-root paths directly and bypass mira-storage.
- knowledge-backup writes project-root knowledge.json and knowledge-backup.json before Drive operations; it is not a read-only backup.
- knowledge-restore writes a safety backup and overwrites project-root knowledge.json before attempting Drive sync; it remains destructive and was not invoked.
- knowledge-search replaces the local candidate array whenever Drive returns any array, including an empty array.

3. CALLER AND DOMAIN MAP EXTENSIONS
- Conversation API routes call conversation-store and Conversation Memory Engine; the persistent file is data/conversations.json via storagePath, not general memory.json.
- Conversation Memory Engine itself delegates persistence to conversation-store.
- Work Learning Engine owns data/work-learning-records.json via storagePath; Experience Memory, Retrieval, Future Strategy, Cross-Task Learning and Learning History are derived/read-oriented layers in the inspected modules and do not establish separate stores in this targeted review.
- Work Knowledge Consolidation owns data/work-knowledge-consolidation.json under storagePath('data').
- Stage13 Learning Governance owns data/stage13-learning-governance.json under storagePath.
- Knowledge improvement proposals and autonomous learning proposals are separate governance stores under storagePath; they are not the approved Knowledge catalog.
- Audit log has a storagePath default plus MIRA_AUDIT_FILE override.
- Snapshot Manager uses project-root backups/changes, outside the mira-storage resolver.
