2. KNOWLEDGE IMPROVEMENT ROUTE — CALLER AND AUDIT ORDER

routes/knowledge-improvements.js is SYSTEM_ADMIN-gated for proposal listing, approval, rejection, apply, and audit-log retrieval.

Approval/rejection:
- Route loads proposal, calls approveProposal/rejectProposal, then attempts audit record.
- The local writeAudit wrapper catches recordAudit exceptions and returns {logged:false,...}; callers do not inspect that result. Therefore proposal mutation may succeed while its audit record fails without the route failing closed.

Apply path:
- Reads proposal and current Knowledge through getProposal/getKnowledge.
- Requires proposal.status === approved.
- Locates original entry by normalized title+topic and checks proposal.existing.contentHash against current content.
- Builds proposed Knowledge state and expectedPreStateHash.
- Calls prepareEvolution, then applyEvolution, then verifyEvolutionState("knowledge").
- On final verification failure, attempts rollbackEvolution when changeId and snapshotId exist.
- Calls markProposalApplied only after successful verification. If proposal marking fails, it attempts rollbackEvolution.
- Successful path writes KNOWLEDGE_IMPROVEMENT_APPLIED audit after apply, verification, and proposal marking.

Audit coverage gap:
- Several early return branches (proposal missing, approval missing, original entry missing, stale proposal, prepare failure, apply failure, final verification failure, proposal commit failure) return without a corresponding route-level audit record.
- The catch branch records APPLY_FAILED, but handled failure returns do not enter catch.
- Thus route-level audit coverage for this apply endpoint is incomplete even though lower-level evolution services may emit their own audit events. This review did not prove whether every lower-level event covers every branch.

3. AUTONOMOUS LEARNING ROUTE — CALLER AND AUDIT ORDER

routes/autonomous-learning.js is SYSTEM_ADMIN-gated.
- Proposal creation calls createAutonomousProposal and records created/duplicate/failed audit outcomes.
- Admin proposal creation writes proposal records only; route comments explicitly state it does not modify knowledge.json.
- Apply requires proposal status approved, records AUTONOMOUS_APPLY_STARTED, calls applyAutonomousLearningControlled, and records success/failure with snapshot, rollback, count, and Drive sync metadata.
- The route reports driveSynced and verified from the controlled apply result.

Audit behavior differs from Knowledge Improvement:
- writeAudit calls recordAudit directly and does not wrap it in a local try/catch. Audit-store failure can therefore affect the route's request path, unlike the swallowing helper in routes/knowledge-improvements.js.
- Empty proposal ID validation returns 400 before an audit event is written.
- Other blocked/not-found apply states are audited.
- The apply controller remains the actual mutation boundary; this route does not directly write Knowledge.

4. LEARNING SERVICE — AUTOMATIC PERSISTENCE AND PROVIDER EGRESS

services/learning.js:
- learnFromContent cleans source text, builds a learning prompt, and calls generate(...) with the prompt as both prompt content and user message, plus a system instruction.
- This is an external-provider egress boundary whenever a live provider is selected; source material and source metadata may be transmitted to that provider. No provider call was made in this review.
- Parsed model output is validated, then searchKnowledge is used for duplicate detection.
- If no duplicate is found, learnFromContent calls addLearning directly.
- addLearning is the Knowledge CRUD path already mapped to local write followed by Drive sync.
- Therefore this function is not merely a proposal generator: its normal non-duplicate path can persist Knowledge/Learning and trigger Drive synchronization without the separate admin proposal/apply route. Caller authorization, consent, and invocation context must be traced at each upstream caller before any provider or persistence redesign.
- Return fields include success, learned, saved, duplicate, drive, title, topic, category, track, and difficulty. A successful learning extraction can return saved=false for duplicate or unsuccessful add; drive is a boolean derived from the addLearning result.

services/mira-experience-memory.js:
