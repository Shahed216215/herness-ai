3. READ-FAILURE SAFETY

3.1 General Memory

memory.js delegates read/write to services/mira-local-memory-store.js. The Local Memory Store:
- Rejects symlinks and non-regular files.
- Rejects empty, invalid JSON, and non-array contents.
- Uses temp-file + fsync + rename, attempts directory fsync, and verifies readback SHA-256 for writes.
- For readMemory(), calls readArray(MEMORY_FILE, ..., missingIsEmpty=true). A missing primary memory.json therefore returns [] rather than a distinct missing/error state.
- MIRA_MEMORY_FILE can override the path using path.resolve(process.env.MIRA_MEMORY_FILE), independently of MIRA_STORAGE_DIR.

This means corruption/read failures are rejected, but a missing primary Memory file is silently represented as empty Memory. HFM-001 remains IDENTIFIED/PARTIAL, not closed. The write implementation is materially stronger than Knowledge CRUD but does not prove cross-process concurrency/CAS guarantees.

3.2 Knowledge

knowledge.js:
- loadKnowledge() returns [] when knowledge.json does not exist.
- JSON parse errors are caught and converted to [].
- Valid JSON whose root is not an array is also converted to [].
- saveLocalKnowledge() uses direct fs.writeFileSync to the target, without the same temp/fsync/rename/readback protocol used by the Memory Store.
- CRUD operations load via loadKnowledge(), then may write the returned array.

Therefore a missing, malformed, or non-array Knowledge file can be treated as an empty database and subsequently overwritten by an add/update/delete workflow. This is direct evidence for HFM-001 and HFM-002 in the Knowledge persistence path, distinct from the stronger General Memory Store.

3.3 Knowledge search and cleanup

tools/knowledge-search.js loads Local Knowledge and then replaces it with any Drive array, including []. A valid empty Drive response can mask non-empty Local Knowledge. A Drive exception retains Local Knowledge. This is a source precedence inconsistency; no canonical authority policy has been approved.

tools/knowledge-cleanup.js writes project-root knowledge.json directly when removing duplicates, then calls saveKnowledgeToDrive(). The operation bypasses mira-storage and uses a non-atomic direct write. The inspect action does not write. The remove action is mutating and was not invoked.

4. STORAGE ROOT AND OVERRIDE RECONCILIATION

4.1 Shared resolver

mira-storage.js:
- Default root is project root.
- MIRA_STORAGE_DIR changes the root.
- storagePath() rejects absolute paths and traversal.
- When a configured root target is absent, it may seed from a bounded regular non-symlink project-root file; secret/token filename patterns are excluded.
- Target directory and symlink checks are performed.

4.4 Implication

When MIRA_STORAGE_DIR is configured, the primary Knowledge and Memory modules may use the configured root while legacy Knowledge cleanup/backup/restore tools still target project-root files. Provider credentials and snapshots also remain project-root scoped. This can create multiple effective roots and split-brain behavior. Existing seeding logic does not automatically reconcile all legacy callers or independent environment overrides.

5. DOMAIN STORE WRITE-PATTERN NOTES

The targeted store inspection confirms materially different write guarantees:
- General Memory Store: unique exclusive temp, mode 0600, fsync, rename, directory fsync attempt, readback hash.
- Knowledge CRUD: direct writeFileSync; no atomic/readback protocol established.
- Project Store: temp file and rename.
- Task Store: temp file and rename; explicit override.
- Opportunity Store: temp file and rename; explicit override.
- Conversation Store: temp file and rename.
- Client Profile Store: temp file and rename; no lock/fsync/readback established in inspected path.
- Client Communication Store: temp file and rename; no lock/fsync/readback established in inspected path.
- Client Follow-up Store: temp file and rename.
- Deliverable Store: temp file and rename.
- Work Acceptance Store: temp file and rename.
- Client Consent Store: exclusive temp/mode 0600 and rename; audit integration is separate.
- SEO Workflow Store: lock directory, exclusive temp, fsync, rename.
- Stage 13 Learning Governance: exclusive temp and rename.
- Work Learning and Work Knowledge Consolidation: resolver-aligned storage and audit calls; distinct schemas.
- Research Governance: lock directory, owner marker, temp file and rename; malformed/unreadable state fails closed.
- Autonomous Orchestrator: lock-protected store wrapper and storagePath default.

This report does not certify all concurrency, crash consistency, or cross-process properties. No runtime tests were run.
