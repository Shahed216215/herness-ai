4. OTHER PERSISTENCE DEPENDENCIES AND DATA FLOWS

- Work Learning is the source of Experience Memory and Experience Retrieval. Experience Memory is currently a normalized projection, not a separate persistent provider.
- Work Learning records are also consumed by Work Knowledge Consolidation. Consolidation validates Learning record integrity and stores derived reusable knowledge separately.
- Work Learning and Work Knowledge Consolidation call the audit subsystem; general Memory and Knowledge operations are not shown to have comprehensive audit coverage.
- Conversation storage is a separate persistent domain with conversations, messages and contexts. It should not be merged blindly into the same retention or access policy as general Memory.
- Evolution snapshots and Local Memory backup/restore are different recovery mechanisms. Neither establishes a unified backup strategy for all stores.
- Storage path resolution is shared by several components, but using a common path resolver does not make their schemas, write guarantees or provider semantics unified.
- Change proposals and approval records are adjacent governance dependencies; they are not treated here as Memory content stores. Any migration must preserve their references and approval state.

5. SAFE MIGRATION ORDER — PROPOSAL ONLY

M0 — Freeze and inventory
- Preserve the existing Drive workflows.
- Freeze the current source baseline and inventory all read/write callsites, file paths, schemas, environment overrides, and tests.
- No production Memory reads, migrations, or provider calls are part of this design step.

M1 — Define canonical contracts in isolation
- Define versioned records with stable IDs, schemaVersion, revision, provenance, timestamps, source references, classification, retention, and integrity metadata.
- Define distinct logical domains for general Memory, Knowledge, Work Learning, derived Experience, Consolidation, Conversation and Audit. Shared provider does not mean shared retention/access policy.
- Define missing-store initialization, corruption, conflict, duplicate, tombstone and recovery semantics.
- Define provider-neutral interfaces and capability declarations; no live adapters yet.

M2 — Build isolated fixture adapters
- Implement and test adapters against temporary fixture directories and in-memory/mock providers only.
- Establish atomic writes, compare-and-swap or serialized writer guarantees, readback verification, conflict quarantine, audit coverage, and deterministic failure behavior.
- Verify that a missing store is distinguishable from an intentionally initialized empty store.

M3 — Add compatibility adapters without deleting existing paths
- Map Local Memory, Knowledge, Learning, Consolidation and Conversation to the new contracts using fixture data.
- Keep Experience as a derived projection until a separately justified persistence requirement is proven.
- Preserve all current public API and proposal references; run offline regression/integration tests against isolated fixtures.

M4 — Migrate each Drive-dependent workflow independently
- D01 Knowledge add/sync semantics.
- D02 Knowledge controlled apply and rollback.
- D03 Autonomous-learning controlled apply and rollback.
- D04 Evolution Memory/Knowledge apply, verification, Drive snapshot and rollback.
- For each: demonstrate replacement behavior, error handling, conflict preservation, idempotency, readback, audit and rollback using isolated tests. Do not switch off Drive for any workflow until its own evidence is reviewed.

M5 — Provider cutover decision
- Only after all workflows have replacement evidence, conduct a separate data classification, encryption/key custody, provider permission and migration plan review.
- Any production dual-read, dual-write, backfill, cutover or Drive decommission requires a new explicit authorization and an independently approved recovery plan.
- Keep emergency backup separate from routine sync and verify restore capability before considering any retirement.

M6 — Acceptance and close
- Run isolated unit, integration, crash/recovery, concurrency, security, compatibility and regression suites.
- Record exact commands, fixture boundaries, outputs, hashes and test status. Unexecuted tests remain NOT_EXECUTED / INCONCLUSIVE.
- Close Phase 1 only after full callsite inventory, schema/ownership review, migration blockers and test evidence are reviewed. Phase 2 changes require separate approval.
