4. CONFIRMED ADDITIONAL FINDINGS

F01 — Conversation persistence is separate from general Memory.
conversation-store.js imports mira-storage and resolves data/conversations.json through storagePath. It performs local directory creation, read/write, and temporary-file rename operations. routes/conversations.js delegates CRUD/context operations to conversation-store and conversation-memory-engine. The conversation-memory-engine delegates persistence to conversation-store. This is a distinct persistence domain and must not be conflated with memory.json.

F02 — Learning and governance stores remain separate persistence domains.
services/mira-work-learning-engine.js uses storagePath('data/work-learning-records.json') unless MIRA_LEARNING_FILE overrides it. The inspected implementation performs local filesystem operations including directory creation, read/write, and rename.
services/mira-work-knowledge-consolidation.js uses storagePath('data') and a separate work-knowledge-consolidation store file.
services/mira-stage13-learning-governance.js uses MIRA_STAGE13_STORE when configured, otherwise storagePath('data/stage13-learning-governance.json'). These are separate data stores and require separate compatibility and migration analysis in any future design.

F03 — Learning-history and experience layers are read/derived service layers in the inspected call chain.
routes/learning-history.js delegates to mira-learning-history and experience-memory. mira-learning-history obtains records from experience-memory and future-strategy-engine. The inspected files did not expose independent file writes for these derived layers. Their source persistence remains upstream and must be traced through the relevant source engines; do not count them as separate durable stores without evidence.

F04 — Knowledge search has a Local/Drive precedence ambiguity.
tools/knowledge-search.js first obtains local Knowledge and then attempts loadKnowledgeFromDrive(). If the Drive result is an array, it replaces the local search source. An empty Drive array is still an array and therefore also replaces the local source. This is confirmed source behavior. The intended authoritative-source and empty-remote-result policy is not established by the inspected code or current design record.

F05 — Knowledge cleanup bypasses the shared storage resolver.
tools/knowledge-cleanup.js constructs KNOWLEDGE_FILE from a project-root path, writes the cleaned local Knowledge file directly, and then calls saveKnowledgeToDrive(). This is inconsistent with the storagePath-based Knowledge module when MIRA_STORAGE_DIR points elsewhere. The cleanup action was not invoked.

F06 — Knowledge backup is not a strictly read-only/local-only operation.
tools/knowledge-backup.js constructs project-root Knowledge and credential/token paths directly, writes local knowledge.json and knowledge-backup.json, and performs Google Drive folder/list/create/update operations to synchronize a backup. Its description says it creates a separate backup without modifying the Knowledge base, but the implementation includes a local knowledge.json write. This path was inspected only; the tool was not invoked and no credentials were read.

F07 — Knowledge restore is destructive and path-divergent.
tools/knowledge-restore.js constructs project-root Knowledge, backup, credentials, and token paths directly. It can load a backup from Drive, write a safety backup, overwrite local knowledge.json, and synchronize restored entries to Drive. The inspected path is destructive and bypasses the shared storage resolver. It was not invoked.

F08 — Controlled apply and Evolution continue to depend on Drive.
autonomous-learning-controlled-apply.js uses storagePath for local Knowledge but also reads/writes Drive state, checks equality, snapshots state, verifies post-apply state, and attempts rollback.
knowledge-controlled-apply.js reads Local and Drive before apply, blocks on mismatch, synchronizes and verifies after apply, and has rollback paths.
knowledge-memory-evolution.js uses storagePath for local Memory/Knowledge while retaining Drive load/save and persisted Drive snapshot logic. These remain blockers to removing routine Drive sync until replacement behavior and regression evidence exist.

F09 — Knowledge CRUD remains Drive-coupled.
knowledge.js uses storagePath('knowledge.json') locally and saveKnowledgeToDrive() through syncToDrive(). The inspected CRUD paths expose Drive synchronization outcomes in returned results. tools/knowledge-save.js and tools/learning-save.js surface Drive status from delegated Knowledge/Learning operations. services/learning.js and routes/autonomous-learning.js expose or propagate Drive sync status from delegated flows. These indirect callers must remain in the caller-compatibility inventory.

F10 — Memory and Knowledge helper tools delegate to modules.
tools/memory-save.js, tools/memory-count.js, tools/memory-restore.js, tools/knowledge-count.js, tools/knowledge-improve.js, and scripts/mira-memory-backup.js are small wrappers or delegates in the inspected files; direct persistence effects are not fully described by their own wrapper text. Their imported module call chains must be included in the caller compatibility map. No helper tool was executed.
