3. BASE KNOWLEDGE CONTRACT

knowledge.js uses storagePath("knowledge.json"), but its read/write contract is weaker than the General Memory Store:
- Missing file -> [].
- JSON parse failure -> log error and [].
- Non-array JSON -> [].
- saveLocalKnowledge() -> direct writeFileSync, without temp/rename/readback verification.
- The async CRUD methods write Local first, then call syncToDrive().
- syncToDrive() catches Drive exceptions and returns false. This can make the operation's local result successful while Drive remains stale.

This is a critical compatibility constraint: any replacement must distinguish missing, empty, malformed, unreadable, and valid-empty states. It must not treat a failed read as a valid empty database.

4. CALLER-BY-CALLER COMPATIBILITY MATRIX

K01 addKnowledge — direct caller tools/knowledge-save.js and other services.
- Reads through loadKnowledge().
- Duplicate key: normalized title + URL + content.
- Duplicate result: status=duplicate_skipped, added=false, duplicate=true, plus drive boolean; even duplicate path attempts Drive sync.
- New record gets stable generated id and savedAt; list is capacity-trimmed; local write then Drive sync.
- Success status=added, added=true, duplicate=false, drive boolean, savedAt.
- Risk: a missing/corrupt read mapped to [] can permit a new array to overwrite prior data; local success can coexist with drive=false.

K02 addLearning — caller services/learning.js and tools/learning-save.js.
- Validates structured learning fields; invalid -> validation_error, added=false, drive=false, errors[].
- Duplicate key: normalized title + topic + content.
- Duplicate -> duplicate_skipped, added=false, duplicate=true, and Drive sync attempt.
- New record has type=learning, topic/category/track/difficulty/title/concept/technique/safeLabExample/defense/detection/source/content/savedAt/id.
- Capacity-trimmed local write then Drive sync.
- Success status=learned, added=true, duplicate=false, drive boolean, entry metadata.
- Same read-failure and partial dual-write risks as K01.

K03 deleteKnowledge — direct/indirect callers not proven exhaustive.
- Loads Knowledge, matches stable id.
- Missing target -> not_found, deleted=false, drive=false.
- Match -> filters entry, local direct write, then Drive sync.
- Result status=deleted, deleted=true, drive boolean, deleted-entry metadata.
- Risk: silent-empty read can turn a delete into not_found or a later unrelated operation into overwrite; deletion is not transactional with Drive.

K04 updateKnowledge.
- Matches stable id.
- Missing target -> not_found.
- Requires non-empty title/content; invalid -> validation_error.
- Duplicate key: normalized title + URL + content, excluding target.
- Duplicate -> duplicate_skipped, updated=false, drive=false.
- Preserves existing stable ID; writes Local, then Drive.
- Result includes status=updated, updated=true, drive boolean, previous and entry metadata.
- Same dual-write/read-failure risks.

K05 updateLearning — callers include services/learning.js and controlled apply.
- Validates structured input; invalid -> validation_error.
- Finds by object title+topic, or id/title string.
- Missing target -> not_found.
- Duplicate equivalent learning -> duplicate_skipped, updated=false, drive=false.
- Preserves existing record fields/ID, writes Local then Drive.
- Result status=updated, updated=true, drive boolean, previous and entry metadata.
- Important: controlled apply explicitly treats updated=true with drive!==true as failure and attempts rollback.

K06 searchKnowledge / tools/knowledge-search.js.
- Reads Local first.
- Loads Drive.
- Any Drive array replaces Local, including [].
- Drive exception logs and keeps Local.
- Empty final array returns "No knowledge entries are currently stored."
- Search performs lexical ranking and duplicate filtering.
- No authoritative source, freshness, version, or conflict resolution is recorded.
- A valid empty Drive response can mask non-empty Local data.

K07 cleanup inspect.
- getKnowledge() -> duplicate grouping only.
- Returns success/action=inspect/totalEntries/duplicateGroups/duplicateEntries/dataModified=false/groups[].
- No write in inspect path.

K08 cleanup remove.
- Re-reads getKnowledge(), removes exact duplicates by normalized title/URL/content.
- If no duplicates: success=true, removed=0, remaining count, driveSync=false; no write.
- If duplicates: direct project-root knowledge.json write (not storagePath), then shared adapter saveKnowledgeToDrive.
- Returns success=true, removed/remaining, driveSync=true and driveAction without independently validating the returned Drive result.
- Direct path divergence and non-atomic write. Not invoked.

K09 Knowledge backup.
- getKnowledge() must return an array.
- Builds backupVersion=1 with createdAt/source/entryCount/entries.
- Writes project-root knowledge.json and knowledge-backup.json directly.
- Independently initializes Google OAuth and uses Drive list/create/update.
- Not a read-only backup. No encryption or independent hash/authenticity check evidenced in inspected backup schema.
- Uses direct project-root path and independent Drive implementation. Not invoked.

K10 Knowledge restore.
- Reads local or Drive backup depending on tool path; Drive OAuth implementation is inline and separate.
- Validates backupVersion=1 and entries array; no cryptographic authenticity check evidenced.
- Creates knowledge-before-restore.json from current project-root file, then overwrites project-root knowledge.json and syncs Drive.
- Existing non-array current content may be treated as [] in safety-backup construction.
- Destructive restore. Never invoked in this review.

K11 Knowledge controlled apply.
- Requires approved proposal with existing/proposed payload.
- Reads Local and Drive; Drive must be array and exactly equal to Local before apply.
- Validates existing entry and expected content hash.
- Creates and verifies local snapshot of knowledge.json.
- Calls updateLearning().
- If update throws, updated!==true, or drive!==true, attempts local snapshot rollback plus Drive restoration/readback.
- Verifies updated Local entry/content and reloads Drive; mismatch triggers rollback.
- The visible source explicitly protects against updateLearning reporting local updated=true while Drive sync failed.
- Rollback success depends on local snapshot restoration and Drive restoration/readback; audit/approval proposal state finalization needs caller-specific verification.

K12 Autonomous learning controlled apply.
- Requires approved proposal and valid learning payload.
- Reads raw Local file and module Local state; requires exact match.
- Reads Drive; requires array and exact Local/Drive match.
- Rejects duplicate, creates and verifies local snapshot, calls addLearning.
- Verifies local count increase, entry existence, Drive array, exact Local/Drive equality and matching hashes.
- Marks proposal applied only after checks.
- Catch path attempts snapshot rollback plus Drive restore/readback; fallback attempts local rewrite and Drive restore if no snapshot.
- Return includes driveSynced=true and verified=true only after the checks.
- Still depends on Knowledge CRUD's read/write semantics and Drive availability.

K13 Stage 4.12 Knowledge/Memory Evolution.
- Uses storagePath for local Memory and Knowledge.
- Uses Drive read/write for both Memory and Knowledge.
- Validates record arrays and record fields.
- Checks preservation of existing entries.
- Compares Local and Drive; permits a constrained prefix reconciliation case only when proposed state equals Local.
- Creates local snapshot, persists a Drive snapshot under project-root backups/changes, verifies both, writes target state, verifies Local/Drive and hashes, audits lifecycle events, and attempts rollback.
- Drive snapshot is JSON with SHA-256 integrity hash; no encryption/authenticity key layer established.
- Snapshot Manager path remains project-root even if MIRA_STORAGE_DIR is configured.
- This is a critical Drive-removal blocker until replacement preserves prepare/apply/verify/audit/rollback/recovery.
